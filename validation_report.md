## Summary

Prepare a concise validation and release-readiness report for `embedded-rf` v1.1.

The goal is to document the current state of the project, verify the software-side checks that can be performed without physical hardware, and clearly identify the remaining work required before the `v1.1.0` release.

## Deliverable

Create:

`docs/v1.1-validation-report.md`

The report must be based on the current repository, existing documentation, tests, and validation commands.

## Report contents

### 1. Validation environment

Record the environment used for validation.

Include only non-sensitive information such as:

- Operating system
- Python version
- PlatformIO version

Do not include:

- Personal usernames
- Email addresses
- Absolute home-directory paths
- Private IP addresses
- Wi-Fi SSIDs
- Wi-Fi passwords or other credentials

### 2. Software validation

Run and record the results of:

- Python unit tests
- Python `compileall`
- PlatformIO ESP32-C3 build
- `git diff --check`

For every check, record whether it passed or failed.

Do not report a check as passed unless it was actually executed successfully.

### 3. v1.1 feature review

Review the current repository and summarize the status of:

- Terminal dashboard
- Web dashboard
- Session replay
- Replay speed controls
- CSV/session logging
- Offline session analysis
- CI configuration
- Windows validation documentation

The report should distinguish between functionality verified by automated/software testing and functionality requiring physical ESP32 hardware.

### 4. Physical ESP32 validation status

Create a separate section for physical hardware validation.

Do not claim that physical validation passed unless the tests were actually performed with an ESP32.

Track at least:

- [ ] Firmware upload to ESP32-C3-DevKitC-02
- [ ] USB serial protocol regression
- [ ] ESP32 Wi-Fi connection
- [ ] Physical TCP control
- [ ] Physical UDP device telemetry
- [ ] TCP/UDP mode synchronization
- [ ] Terminal dashboard with physical ESP32
- [ ] Web dashboard with physical ESP32
- [ ] Browser STATUS / ON / OFF controls with physical ESP32

If hardware is unavailable, explicitly mark these items as pending rather than failed.

### 5. Release-readiness checklist

Include a checklist similar to:

#### Software

- [ ] Python test suite passes
- [ ] Python compile checks pass
- [ ] PlatformIO ESP32-C3 build passes
- [ ] Session replay verified
- [ ] Web dashboard/replay verified
- [ ] `git diff --check` passes
- [ ] Documentation reviewed

#### Hardware

- [ ] Physical ESP32 validation completed
- [ ] USB regression completed
- [ ] Wi-Fi/TCP/UDP validation completed
- [ ] Physical dashboard integration completed

#### Release

- [ ] Final full regression completed
- [ ] Repository worktree verified clean
- [ ] No credentials or generated artifacts tracked
- [ ] `v1.1.0` release smoke test completed
- [ ] `v1.1.0` tag/release ready

Only mark items `[x]` when they have actually been verified.

## Simulation / telemetry clarification

The report must preserve the project's distinction between simulated RF data and real device telemetry.

RSSI, noise, and packet-success values generated by the simulator are software-generated values and must be identified as:

`SIMULATED RF`

They must not be described as physical ESP32 RF measurements.

ESP32 UDP telemetry is device/control telemetry and must not be presented as RF measurement data.

## Safety and privacy

Do not include or expose:

- `wifi_config.h` contents
- Wi-Fi credentials
- Real SSIDs
- Private LAN IP addresses
- Personal email addresses
- Private hardware logs
- Machine-specific absolute paths
- `.venv`
- `.pio`
- `__pycache__`
- Generated private CSV/report/plot artifacts

Do not add real RF interference or jamming functionality.

## Scope

This issue is primarily a documentation and validation task.

Avoid unrelated source-code changes.

If a software problem is discovered during validation, document it accurately rather than making unrelated changes as part of this issue.
